# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

tapSynth is a JUCE audio plugin synthesizer (C++17, `pluginIsSynth`, MIDI in). It adds a natural-language text prompt: the user describes a timbre, and the editor sends it to the Google Gemini API, which returns JSON that sets the plugin's parameters. UI strings are partly in Portuguese ("Enviar", "Gerando...", "Descreva um timbre...").

## Build

CMake (3.22+) with JUCE 8.0.9, downloaded at configure time via FetchContent (pass `-DTAPSYNTH_JUCE_DIR=/path/to/JUCE` to use a local checkout instead):

```bash
cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
```

Output goes to `build/tapSynth_artefacts/<Config>/`. Formats are VST3 on all platforms, plus AU on macOS only (AU is Apple-only). On Windows, use the default Visual Studio generator and `cmake --build build --config Release`. On Linux, the JUCE dependencies are listed in `.github/workflows/build.yml` (ALSA, X11, freetype, fontconfig, libcurl). libcurl is required, since `JUCE_USE_CURL=1` is what makes the Gemini HTTPS request work on Linux.

CI (`.github/workflows/build.yml`) builds Linux, Windows and a universal macOS binary on every push. `.github/workflows/tests.yml` builds and runs `tapSynth_tests` on the same three systems and uploads a JUnit XML report.

New source files must be added to `target_sources` in `CMakeLists.txt`. `JuceHeader.h` is generated by `juce_generate_juce_header`.

Tests: `tests/` builds the `tapSynth_tests` executable (GoogleTest, fetched at configure time; disable with `-DTAPSYNTH_BUILD_TESTS=OFF`). It links the plugin's shared-code library (the `tapSynth` target) and borrows its include paths and definitions, so the JUCE modules are not compiled twice. Run with `cmake --build build --target tapSynth_tests && ctest --test-dir build`. There is no lint configuration.

Test layout: `tests/common/` has `render()` (real processor, MIDI notes, optional JSON patch through `applyParametersFromJson`), the audio measurements (`Analysis.h`), the tolerances and grids (`Tolerances.h`), and `within()` (`Check.h`), which records each measured value in the XML report as `<tolerance>|<label>` and asserts the default. Suites, one per strategy: `Sanity*`, `Spectral*`, `Temporal*`, `Golden*`; `AnalysisSelfTest` checks the measurements on synthetic signals and is not a strategy. Golden references are 32-bit float WAVs in `tests/references/`, recorded with `TAPSYNTH_RECORD_GOLDEN=1 tapSynth_tests --gtest_filter='*Golden*'`. `tapSynth_tests --tapsynth-list-tolerances` prints every tolerance and grid as JSON.

Local tools (ignored by git, in `tools/`): `tools/pluginval/pluginval` (v1.0.4), Mull 0.36 for LLVM 19 extracted to `tools/mull/usr/bin/` (`mull-runner-19`), and a JUCE 8.0.9 clone in `tools/JUCE` for builds with `-DTAPSYNTH_JUCE_DIR`.

## Architecture

**Parameters are the central contract.** All synth state lives in `TapSynthAudioProcessor::apvts` (an `AudioProcessorValueTreeState`), and parameters are declared in `createParams()` in `Source/PluginProcessor.cpp`. Parameter string IDs (`"OSC1GAIN"`, `"FILTERCUTOFF"`, etc.) are repeated in four places that must be kept in sync whenever a parameter is added, renamed, or has its range changed:
- `createParams()`, which defines the ID, range, and default
- `setVoiceParams()` / `setFilterParams()` / `setReverbParams()`, which read the raw values every `processBlock` and push them into the DSP
- the `TapSynthAudioProcessorEditor` constructor initializer list, which passes the IDs to the UI panels (each control cell uses its parameter ID as its component ID, which is how the AI-changed highlight finds it)
- the hardcoded LLM prompt in `TapSynthAudioProcessorEditor::sendPrompt()` (`Source/PluginEditor.cpp`), which lists every ID and range for Gemini. Choice parameters are sent as integer indices.

**Audio path:** `juce::Synthesiser` with 5 `SynthVoice`s and a single `SynthSound`. For each voice, processing runs as osc1 + osc2 (`OscData`, a `juce::dsp::Oscillator` subclass with FM and gain) → fixed gain → amp ADSR → per-channel `FilterData` (type/resonance/base cutoff/mod depths are pushed each block via `updateModParams`). After the voices are summed, the processor applies a `juce::dsp::Reverb` and then `MeterData` (per-channel RMS over a 300 ms window, plus a peak that `takePeak()` reads and resets once per UI frame). Voices hold per-channel `std::array`s of size 2 (stereo is assumed). Filter cutoff is recomputed every sample in `SynthVoice::renderNextBlock` as base cutoff + filter-ADSR × depth + LFO × depth, clamped to [20 Hz, min(20 kHz, 0.49·fs)]. OSC FM offsets the note in semitones per sample (`OscData::updateFrequency`).

**Directory split:** `Source/Data/` holds DSP wrapper classes (no UI). `Source/UI/` holds the editor, built to the tapSynth design system (fixed 1066 × 600 window, dark, flat vector drawing):
- `TapLookAndFeel.h/.cpp`: the design tokens in `namespace Tap` (colours, the `osc`/`filter`/`accent` module groups, IBM Plex Sans type styles, value formatting with a real minus sign and a thin space before units) and the LookAndFeel that draws knobs, vertical sliders and tooltips. Sliders read their group, bipolar flag and AI-highlight alpha from `getProperties()`.
- `CustomComponent.h/.cpp`: `TapPanel` (numbered module panel; child coordinates are measured from inside its 1 px border via `inset`) and the control cells `KnobCell`, `SliderCell`, `SegmentedSelector`, `ToggleCell`, which all implement `AiTarget`.
- `Displays.h/.cpp`: oscillator, filter-response, envelope and LFO displays. They poll the raw parameter values from the editor's 30 Hz timer (`TapPanel::tick`) and repaint on change.
- One panel class per module (`OscComponent`, `FilterComponent`, `AdsrComponent` for both envelopes, `LfoComponent`, `ReverbComponent`, `MeterComponent`), placed with the coordinates from the design's layout table.
- `PromptBar.h/.cpp`: the AI prompt bar (idle / typing / generating / success / error, with feedback shown inline and never in dialogs) and the preset box.

The fonts are `Resources/Fonts/IBMPlexSans-*.ttf` (SIL OFL), embedded through the `tapSynthFonts` binary-data target. UI strings with accents must go through `Tap::utf8()`, because `juce::String (const char*)` assumes ASCII. `Source/UI/Assets.cpp` (an embedded PNG logo) is no longer used; the logo mark is drawn with paths.

**AI prompt flow (`sendPrompt`):** a detached `std::thread` POSTs to `https://generativelanguage.googleapis.com/v1beta/models/<model>:generateContent` with an `x-goog-api-key` header. The API key is read at runtime from the `GEMINI_API_KEY` environment variable (the prompt bar shows "Defina GEMINI_API_KEY" when it is missing). Never write a real key in any file. The result goes back to the editor on the message thread through a `Component::SafePointer` (`handleResponse`), since the editor may be closed mid-request. There, `candidates[0].content.parts[0].text` is parsed as JSON and `applyAiPatch` passes it to `TapSynthAudioProcessor::applyParametersFromJson`, which logs unknown IDs with `DBG`. `applyParametersFromJson` uses `convertTo0to1` + `setValueNotifyingHost`, so out-of-range values are clamped and hosts see the change. `applyAiPatch` diffs parameter snapshots taken before and after, so it can highlight the controls that changed, offer "Desfazer" (undo), and append the patch to `sessionPatches` (the preset box's per-session history, kept on the processor and not saved with the state). Errors are shown as short Portuguese messages in the prompt bar, and the details go to `DBG`.

Plugin state is the APVTS `ValueTree` serialised as XML (`getStateInformation`/`setStateInformation`). Parameters use `juce::ParameterID { id, 1 }`, so a newly added parameter should get version hint 2 (or higher) to keep AU/VST3 hosts stable.

## Estudo de testes (TCC)

Este repositório é o objeto de um estudo sobre testes automatizados de áudio.
O plano completo está no doc "Plano do estudo: testes automatizados de áudio no tapSynth".

- Testes ficam em tests/ e usam GoogleTest; o executável tapSynth_tests liga a biblioteca tapSynth.
- Todo teste renderiza áudio pelo TapSynthAudioProcessor real (sem editor), via `tapsynth::test::render` em tests/common/Render.h.
- Não leia, crie nem altere nada em experiment/faults/. Não escreva testes pensando em defeitos específicos.
- Não leia o conteúdo de mutantes do Mull (diffs, linhas, operadores) antes da tag tests-frozen; contagens por arquivo são permitidas.
- Depois da tag tests-frozen, não altere arquivos em tests/.
- Tolerâncias ficam em tests/common/Tolerances.h e só mudam com aprovação explícita.
- Nunca escreva uma chave de API em nenhum arquivo.
